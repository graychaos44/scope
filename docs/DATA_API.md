# 기록 API·데이터폼 규격 (2026-08-13)

> 사용자 08-13:
> *"이것도 API 를 정해서 데이터폼 만들어서 나중에 외부 프로그램이나 라이브러리를 연결할 수 있게 하자."*
> *"내가 전부터 계속 **여유를 주라**고 했었는데, 이런 실험·테스트용 프로그램은 **확장성**이 중요해.
>  아까 보여준 프로그램 스샷 보면 항목이 엄청 많이 추가되는 걸 알 수 있어.
>  우리도 무제한은 아니지만 **카테고리와 항목 데이터, 필요한 것들 다 뽑을 수 있게** 해야 해."*

★**여기에는 차원 상한이 없다.** 어댑터·코어의 상한(obs 100·act 20)은 **증류 비용과 성능** 때문인데,
  기록 형식에는 그 이유가 없다 — 항목이 늘어도 학습이 무거워지지 않는다. 자세한 것은 6절.
  빡빡한 규격은 항목이 하나 늘 때마다 형식을 다시 만들게 한다 — 그러면 옛 기록을 못 읽는다.

---

## 1. 확장을 막는 설계 vs 여는 설계

| 막는 설계(하지 않는다) | 여는 설계(이렇게 한다) |
|---|---|
| 열이 고정된 표(칸을 미리 다 정함) | **이름→값 사전** — 항목 추가 = 키 하나 추가 |
| 카테고리가 코드에 박힘 | **점으로 나눈 이름**(`core.health.dead_units`) — 새 갈래를 그냥 만든다 |
| 모르는 키를 만나면 오류 | **모르는 키는 건너뛴다** — 옛 도구가 새 기록을 읽어도 안 죽는다 |
| 아무 이름이나 쓴다 | **항목 사전에 등록**해야 쓴다(오타·중복 방지). 등록은 한 줄 |

★핵심은 **"옛 기록과 새 기록이 같이 살 수 있는가"** 다. 항목을 늘려도 옛 파일을 못 읽게 되면 안 된다.

## 2. 데이터폼 — 실행 하나의 모양

표준을 따른다. 실험 기록의 사실상 표준은 **MLflow 방식**이다:
`실행 하나 = 설정(params) + 지표(metrics) + 산출물(artifacts) + 꼬리표(tags)`.
외부 도구들이 이미 이 형태를 읽으므로, 우리가 이 모양이면 **나중에 그냥 붙는다.**

```
실행(run)
 ├ run_id          이 실행의 고유 이름
 ├ schema_version  기록 형식 판(★없으면 나중에 못 읽는다)
 ├ params          설정 — 바꾸면 결과가 달라지는 것 (에피·시드·결정규칙·코어해시·개입)
 ├ metrics         지표 — 재서 나온 숫자 (이름→값, 시각이 붙을 수 있음)
 ├ artifacts       산출물 경로 (체크포인트·궤적·그림)
 └ tags            꼬리표 (기기·사람·목적·관련 대장번호)
```

★`params` 와 `metrics` 를 가르는 기준: **내가 정한 것**이면 params, **재서 나온 것**이면 metrics.
  이게 갈려야 나중에 "설정 → 결과" 예측(대리 모델)이 성립한다.

## 3. 카테고리 (상한 없음 — 지금 쓰는 8개)

★카테고리 수에 **상한을 두지 않는다**(6절). 아래는 지금 쓰는 것이고, 필요하면 늘린다.

| 이름 | 무엇 | 예 |
|---|---|---|
| `run` | 실행 조건 | `run.episodes` · `run.seeds` · `run.decision_rule` |
| `env` | 게임 자체 | `env.obs_dim` · `env.ep_len_mean` · `env.timeout_rate` |
| `env.demand` | **게임이 요구하는 능력** | `env.demand.perception` · `env.demand.timing` |
| `result` | 결과 | `result.winrate` · `result.score` · `result.ci95` |
| `core.health` | **학습 건강** | `core.health.dead_unit_ratio` · `core.health.weight_delta` |
| `core.capability` | **코어가 가진 능력** | `core.capability.perception` · `core.capability.memory` |
| `gap` | **요구 − 보유** | `gap.timing` ← 다음에 무엇을 학습시킬지의 근거 |
| `resource` | 자원 | `resource.cpu_seconds` · `resource.peak_ram_gb` |
| *(추가 자유)* | 필요하면 새 카테고리를 만든다 | 등록·이름 규칙만 지킨다 |

★`core.health` 와 `core.capability` 는 **다른 것**이다. 건강은 *"학습이 망가지고 있나"*,
  능력은 *"뭘 할 줄 아나"*. 08-12 에 둘이 어긋났다 — 지표(건강)는 그대로인데 성능이 8.5%p 올랐다(V675).
  **둘 다 있어야** 그런 것이 잡힌다.

## 4. 항목 사전 (이름·단위·의미를 반드시 적는다)

항목마다 **네 가지**를 등록한다. 등록 없이 쓰면 검측기가 잡는다.

| 칸 | 예 |
|---|---|
| 이름 | `result.winrate` |
| 단위 | **`ratio_0_1`** (0~1) — `percent_0_100` 과 반드시 구분 |
| 의미 | "판정축 표집 기준 승률" |
| 방향 | 클수록 좋음 / 작을수록 좋음 / 방향 없음 |

★★**단위를 안 적어서 사고가 났다**(07-27): 한쪽은 비율(0~1), 다른 쪽은 퍼센트(0~100)로 재서
  승률 100% 인 종목을 `1.0 ≤ 8.89` 로 읽었다. 관문 26건이 허위 발화하고, 동시에 진짜 결함은
  **구조적으로 0건**이 됐다. 단위를 규격에 박으면 이 사고가 원리적으로 안 난다.

## 5. 연결(API) — 세 층

| 층 | 무엇 | 언제 |
|---|---|---|
| **1. 파일 규격** | 형식 자체가 계약. 누구든 파일만 읽으면 된다 | **지금** |
| 2. 읽기 라이브러리 | 파이썬에서 `import` 해서 쓰는 함수 (나중에 Rust 로 흡수) | 형식이 굳은 뒤 |
| 3. 소켓·HTTP | 실시간으로 다른 프로그램에 흘려보냄 | 필요해지면 |

★**1층이 제일 중요하다.** 규격만 제대로면 2·3층은 언제든 얹는다.
  반대로 규격이 흔들리면 2·3층을 다시 만들어야 한다.

## 6. ★상한을 두지 않는다 — 여기는 어댑터가 아니다 (사용자 정정 2026-08-13)

> 사용자: *"이 프로그램은 어댑터가 아니니 제한 없이 늘어날 수 있게 해야지.
>  무작정 막 늘어나면 안 되지만, 나중에 **어댑터 데이터를 다른 식으로 복합 조합했을 때** 데이터를 만든다면,
>  지금 제한해 놓으면 그때 가서 고치기 힘들잖아."*

★팀장이 초안에서 **카테고리를 8개 + 여유 2자리로 제한**했다. **틀렸다.**
  규약 §6 의 "여유 +20%" 는 **모델 그릇**(obs 100·act 20·드라이버 슬롯) 이야기이고,
  그 상한이 있는 이유는 **증류 비용과 성능** 이다. 기록 형식에는 그 이유가 없다 —
  항목이 늘어도 학습이 무거워지지 않는다.
  실수 모음집 **M3**("표준을 가져오면서 그 표준의 전제를 안 가져온다")를 그대로 반복했다.

| 대상 | 상한 | 이유 |
|---|---|---|
| 어댑터·코어 차원 | **있다**(obs 100 · act 20) | 증류·성능 |
| 기록 카테고리·항목 | ★**없다** | 늘어도 비용이 안 붙는다 |

### 그러면 "무작정 막 늘어나는 것" 은 무엇으로 막나

상한이 아니라 **규율**로 막는다:

| 규율 | 무엇 |
|---|---|
| 등록제 | 새 항목은 사전에 **이름·단위·의미·방향** 네 칸을 적어야 쓴다 |
| 이름 규칙 | `카테고리.하위.항목` 형태. 아무 데나 새 최상위를 만들지 않는다 |
| 소비자 표시 | 항목마다 **누가 읽는지**를 적는다. 6개월간 읽는 곳 0 이면 `휴면` 으로 내린다 |
| 중복 검사 | 같은 것을 다른 이름으로 두 번 넣지 않는다(검측기가 잡는다) |

★**상한은 확장을 막고, 등록제는 난립을 막는다.** 우리에게 필요한 것은 뒤쪽이다.

### 복합·파생 기록도 같은 형식으로 (사용자가 짚은 그 경우)

*"어댑터 데이터를 다른 식으로 복합 조합했을 때"* 나오는 새 자료도 **같은 데이터폼**에 담긴다.
그러려면 **출처**가 있어야 한다:

```
실행(run)
 ├ derived_from : [원본 run_id, ...]     ← 무엇을 합쳐 만들었나
 ├ derivation   : "어떻게 합쳤나"(방법 이름 + 설정)
 └ (나머지는 동일)
```

★이 두 칸이 있으면 **몇 겹으로 조합해도** 같은 형식으로 표현된다.
  나중에 "이 결과가 어느 원본에서 왔나" 를 거슬러 올라갈 수 있다.
★없으면 파생 자료가 **출처 불명**이 되고, 그때 형식을 고치려면 옛 기록을 전부 손봐야 한다 —
  사용자가 말한 *"그때 가서 고치기 힘들다"* 가 정확히 이것이다.

## 7. 하지 않을 것

- 카테고리를 코드에 하드코딩하지 않는다(P1). 사전 파일에서 읽는다
- 지표를 늘리기만 하고 **아무도 안 보는 상태로 두지 않는다** — 도구 41개 중 33개가 호출처 0 이었다(V691)
- 내부 지표에 **합격·불합격을 매기지 않는다** — 결과와의 상관이 확인되기 전에는 표시만(V675)

## 8. 붙일 AI 모델 — 분석과 시뮬레이션은 크기가 다르다 (사용자 08-13)

> *"우리가 지금 여기서 끝내면 그렇겠지만 이것들이 점점 커질 거고, **년 단위로 가면 처음 작게 만들면
>  나중에 힘들어져.** 그리고 이 프로그램은 **분석 및 시뮬레이션**이 가능해야 해.
>  여기서 큰 부하는 시뮬레이션이야. 그런데 **시뮬레이션을 돌릴 수 있는 신경망이 작지는 않을 거야.**"*

★맞다. 팀장이 앞 절에서 "작은 모델" 이라고 한 것은 **분석 쪽**만 본 것이다. 둘을 갈라 적는다.

### 두 종류를 가른다

| | 분석 모델 | **시뮬레이션 모델** |
|---|---|---|
| 하는 일 | 기록을 읽고 판정·예측 (설정 → 결과) | **실제로 안 굴리고 결과를 만들어낸다** |
| 표준 이름 | 대리 모델(surrogate) · 베이즈 최적화 | **세계모델**(world model) |
| 크기 | 아주 작다 (KB~MB) | ★**크다** (수천만~수억 파라미터) |
| 자원 | CPU 로 충분 | **GPU 필요** |
| 재료 | (설정 → 결과) 표 | **궤적**(obs·행동·보상·다음상태) |
| 우리 상태 | 표가 49줄뿐 | ★씨앗 있음 — `reason_lookahead` 의 WM |

★**시뮬 모델의 씨앗은 이미 있다**: 08-12 에 만든 세계모델이 다음 상태·보상·종료를 예측한다
  (홀드아웃 Δobs MSE 0.002~0.047 · 종료 정확도 99.6~100%). 지금은 아주 작지만 **자리는 그것이다.**

### 자리를 크게 잡아 둔다 (년 단위 대비)

| 항목 | 지금 | 나중에 필요한 것 |
|---|---|---|
| 모델 개수 | 1개(종목별 작은 WM) | **여러 개 교체·병행** — 종목별·계열별·통합 |
| 크기 | 수십만 | 수천만~수억 |
| 두는 곳 | 아수스 CPU | **CUDA 2대**(아수스 5070Ti · 149 3060). 부족하면 원격 배치 |
| 저장 | 파일 하나 | **판 관리**(버전·해시·어느 자료로 배웠나) |
| 호출 | 코드에서 직접 | **경계를 둔다** — 로컬/원격 어디에 있어도 같은 방식으로 부른다 |

★**지금 당장 큰 모델을 만들지는 않는다.** 다만 **자리를 좁게 파지 않는다**:
  ①모델이 여러 개일 수 있다 ②GPU 기기에 있을 수 있다 ③판이 바뀔 수 있다 —
  이 셋을 처음부터 가정하고 인터페이스를 만든다. 나중에 바꾸려면 부르는 곳을 전부 고쳐야 한다.

### ★규율 — 시뮬 결과와 실측을 절대 섞지 않는다

규약 §9-1: **"시뮬레이션 수치는 30%만 믿는다."**
시뮬 모델이 아무리 커져도 이 규율은 유지한다. 기록에 **반드시 표시**한다:

| 표시 | 뜻 |
|---|---|
| `source: measured` | 실제로 굴려서 나온 값 |
| `source: simulated` | 시뮬 모델이 만들어낸 값 |
| `source: predicted` | 분석 모델이 예측한 값 |

★이 칸이 없으면 시뮬값이 대장에 실측처럼 섞인다. 그러면 판정이 통째로 오염된다.
★단 규약도 이렇게 적고 있다 — *"시뮬↔실측 짝이 쌓이면 그때 계수를 다시 정한다."*
  그 짝을 쌓는 것도 이 기록 규격이 하는 일이다.

### 단계 (데이터가 쌓이는 대로)

| 데이터 | 분석 모델 | 시뮬 모델 |
|---|---|---|
| 지금(~50줄) | **없음** — 통계·규칙만 | 종목별 작은 WM(있음) |
| 100~300줄 | 가우시안 프로세스(불확실성을 같이 냄) | 계열 단위 WM |
| 300~1000줄 | 부스팅 회귀 | 더 큰 WM · GPU 학습 |
| 1000줄+ | 신경망 검토 — 또는 **심판에 통합** | 통합 시뮬 |

★**계급도 주의**(규약 §9-0-1): 대리 모델이 하는 일("어디에 힘을 줄지")은 **심판이 할 일과 겹친다.**
  그러니 이것은 **심판 대신이 아니라 심판의 재료**다. 초반엔 팀장이 쓰고, 쌓이면 심판이 가져간다.
